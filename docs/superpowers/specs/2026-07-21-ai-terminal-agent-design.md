# FleurTerm AI 终端代理与会话界面设计规格

日期：2026-07-21

## 1. 背景

当前 AI 面板把模型输出中的 `<terminal-command>` 和 `<fleurterm-action>` 标签解析为可执行动作。`fullAccess` 模式能够执行终端命令、等待一段输出并再次请求模型，但 `ask` 模式在用户点击“运行”后只向终端写入命令，不等待结果、不把结果回传给模型，而且当前 AI 轮次已经变为 `idle`。`auto` 模式同样只触发动作，不形成“模型请求工具 → 执行工具 → 返回结果 → 模型继续”的闭环。

因此，等待审批、等待终端输出或命令阻塞时，界面无法准确表示 AI 仍处于活动会话，也无法像 Codex 一样恢复当前轮次。现有工具按钮缺少执行状态、结果、拒绝与错误记录，AI 面板整体也缺少清晰的对话层级。

## 2. 目标

- 建立与模型供应商无关的终端工具调用模型和可恢复会话状态机。
- 统一 `ask`、`auto`、`fullAccess` 三种执行路径，形成完整工具调用循环。
- 等待审批、执行命令、等待输出和命令阻塞时，AI 保持活动会话状态。
- 命令完成、拒绝、失败或使用部分输出后，把结构化工具结果交给模型继续当前轮次。
- 重新设计 AI 面板，清晰展示用户消息、助手内容、工具调用、审批、执行状态和输出。
- 保持 OpenAI、Anthropic、本地与自定义兼容接口的现有可用性。

## 3. 非目标

- 本次不把 AI 代理迁移到 Rust 后端或独立进程。
- 本次不要求所有模型供应商立即支持原生 function calling / tool use。
- 本次不实现文件系统编辑、网络请求、Git 或外部 MCP 工具。
- 本次不允许 AI 绕过现有命令策略或用户审批。
- 本次不替换终端 PTY、会话生命周期、输出确认或分屏模型。
- 本次不实现跨应用重启的未完成工具调用恢复。

## 4. 方案决策

采用“供应商无关的内部 ToolCall + 现有标签协议适配器”。模型响应仍可使用现有标签协议，解析器把标签转换为统一的工具调用对象；会话执行器只依赖 ToolCall，不再直接依赖标签文本。以后可以为 OpenAI 和 Anthropic 增加原生工具调用适配器，而不改会话状态机和界面。

不采用立即全面切换原生工具协议，因为自定义 OpenAI 兼容服务和本地模型的支持差异较大，会扩大本次风险。也不采用 Rust 后端代理，因为当前终端输出与前端工作区状态已经在 Pinia 中维护，跨进程迁移会引入不必要的协议和恢复复杂度。

## 5. 会话状态机

AI 会话状态使用明确的有限集合：

- `idle`：没有活动轮次；
- `thinking`：等待模型开始响应；
- `streaming`：接收助手文本；
- `awaitingApproval`：工具调用等待用户批准或拒绝；
- `runningTool`：已向终端提交命令；
- `waitingTerminal`：等待命令完成标记或新的终端输出；
- `blocked`：命令未完成、等待交互输入或超过等待窗口；
- `continuing`：工具结果已加入上下文，模型正在继续当前轮次；
- `failed`：当前轮次无法继续；
- `stopped`：用户主动终止当前轮次。

除 `idle`、`failed`、`stopped` 外，其余状态都属于活动会话。活动会话期间保留停止按钮，输入区不启动新的并行轮次。

状态转换必须由单一会话执行器负责，组件不得在多个事件处理器中分散设置状态。每次状态转换同时更新当前工具卡状态和用户可见状态文案。

## 6. 工具调用模型

终端工具调用至少包含：

- 稳定调用 ID；
- 工具类型 `terminal.command`；
- 命令文本；
- 目标会话 ID；
- 请求时间；
- 风险级别；
- 当前状态；
- 捕获输出；
- 退出信息或阻塞原因；
- 用户审批结果。

工具状态使用 `proposed`、`approved`、`denied`、`running`、`blocked`、`completed`、`failed`、`cancelled`。状态含义固定，界面文案通过本地化映射生成，不直接把枚举名展示给用户。

现有应用动作继续通过 `AiAppAction` 执行，但在 UI 中也使用工具卡展示。终端命令是本次闭环执行和结果回传的重点；无法返回可靠结果的应用动作必须返回明确的“已提交”或错误结果，不得让模型声称未验证的成功。

## 7. 命令策略

- `suggest`：只展示命令建议，不进入工具执行循环；
- `ask`：所有终端命令进入 `awaitingApproval`；
- `auto`：只读、低风险命令可以自动执行；具有写入、删除、安装、权限、网络发布或其他副作用的命令仍进入审批；
- `fullAccess`：终端命令自动执行，但仍展示执行状态、允许停止，并受最大工具步数限制。

风险分类器必须默认保守。无法可靠分类的命令视为需要审批。用户拒绝时生成 `denied` 工具结果并交给模型，模型可以解释、调整方案或结束任务，不能静默丢弃。

## 8. Codex 式工具循环

一次活动轮次按以下流程运行：

1. 用户消息加入会话，状态进入 `thinking`。
2. 模型流式输出时进入 `streaming`。
3. 解析到终端工具调用后创建工具卡。
4. 根据命令策略直接执行或进入 `awaitingApproval`。
5. 批准后锁定目标终端会话，写入命令并进入 `runningTool` / `waitingTerminal`。
6. 命令完成后生成包含命令、输出、完成状态和错误的工具结果。
7. 工具结果加入本轮模型上下文，状态进入 `continuing`，模型继续响应。
8. 模型没有新的工具调用时结束轮次并回到 `idle`。

同一轮最多执行六个工具步骤，达到上限后停止自动循环并提示用户。每个工具结果必须与调用 ID 关联，禁止把不同命令的输出混入同一个无标识 system 文本。

## 9. 终端完成与阻塞

命令执行绑定命令开始时的会话 ID 和输出游标，后续即使用户切换标签，也从原目标会话收集输出，禁止错误读取新的焦点终端。

终端执行器优先使用 shell 对应的完成标记判断命令结束；不能安全包装的命令使用输出静默与最大等待时间作为降级路径。命令没有完成标记、持续等待输入或超过等待窗口时进入 `blocked`，AI 仍保持活动状态。

阻塞工具卡提供：

- “继续等待”：保持当前调用并重新等待；
- “中断”：向原目标终端发送中断并返回 `cancelled` 结果；
- “使用当前输出继续”：把已经捕获的部分输出作为 `partial` 结果交给模型。

没有活动终端、目标终端关闭、写入失败或输出监听失败时进入 `failed`，错误显示在对应工具卡中，并允许模型基于失败结果继续解释。

## 10. 审批交互

审批卡明确显示完整命令、目标终端和风险说明，并提供“批准”和“拒绝”。审批期间：

- AI 会话状态保持 `awaitingApproval`；
- 当前工具调用 Promise 保持未完成；
- 输入区不发送新的并行请求；
- 停止操作取消当前轮次并关闭审批；
- 面板关闭和重新打开不会清除内存中的审批卡；
- 用户批准或拒绝后从同一执行点恢复，不新建用户消息。

## 11. AI 面板视觉设计

AI 面板采用清晰的纵向时间线，不使用大量连续边框：

- 头部显示“AI 助手”、当前模型和简洁状态点；
- 用户消息使用紧凑灰色气泡，助手正文使用无气泡阅读区；
- 工具调用使用独立灰阶卡片，左侧状态图标，顶部展示状态和耗时；
- 命令使用等宽字体，输出区域默认显示摘要，可展开完整输出；
- `awaitingApproval` 使用蓝色强调，`running` 使用动态状态，`blocked` 使用琥珀色，失败使用红色；
- 思考、流式输出、运行和阻塞在对话流中保留可见状态；等待审批通过输入区上方的固定审批栏持续可见，不只改变发送按钮文字；
- 输入区改为圆角编辑器容器，操作按钮与状态提示置于底部工具行；
- 保持面板可拖动调整宽度、Markdown、代码块和表格能力。

### 11.1 审批栏位置

待审批工具调用不作为普通工具卡插入对话时间线。AI 状态进入 `awaitingApproval` 后，在输入区正上方显示固定审批栏，避免审批操作随着消息滚动或与已完成工具结果混在一起。

- 审批栏固定在输入区上方，不跟随对话内容滚动；
- 对话时间线不渲染状态为 `proposed` 的终端工具卡；
- 审批栏展示完整命令、目标终端、风险提示、批准和拒绝操作；
- 同一时刻只展示当前等待决策的工具调用；
- 批准或拒绝后审批栏立即退出，工具调用以新的状态回到时间线；
- 已批准、运行中、阻塞、完成、失败和取消的工具调用继续在时间线中展示；
- 面板关闭再打开时，只要审批仍未解决，固定审批栏必须恢复显示。

动画只用于流式光标、运行状态和工具卡状态切换，并尊重 `prefers-reduced-motion`。

## 12. 组件与模块边界

- `aiClient`：只负责供应商请求、流式解析和标准化模型响应；
- `aiToolProtocol`：把标签或未来原生工具调用转换为统一 ToolCall / ToolResult；
- `aiConversationRunner`：唯一的会话循环与状态转换入口；
- `terminalToolRunner`：绑定目标会话、执行命令、收集输出、继续等待和中断；
- `aiCommandRisk`：保守分类命令风险；
- `aiConversationStore`：保存消息、活动轮次状态、工具调用和审批状态；
- `AIPanel`：只负责渲染、收集用户操作并调用 runner，不直接编排多步模型请求；
- `AiToolCard`：展示固定审批栏以及时间线中的运行、阻塞、输出和结果状态。

这些模块通过明确类型通信，避免继续扩大当前 `AIPanel.vue` 中的网络、终端、状态机和展示职责。

## 13. 错误处理与取消

- 停止操作同时取消模型请求和当前终端等待，但不删除已产生的消息、工具卡和部分输出；
- 模型流失败保留用户消息并允许重试；
- 工具失败作为 ToolResult 返回模型，除非用户停止整个轮次；
- 面板卸载不得遗留未处理的审批 Promise、输出监听器或事件监听器；
- 所有超时和中断必须释放监听器；
- 工具输出按字节上限截断，并明确标注截断，避免把无限终端输出发送给模型。

## 14. 测试与验证

自动化测试覆盖：

- 状态机合法转换和活动状态判断；
- `ask` 批准、拒绝和停止后的原地恢复；
- `auto` 低风险自动执行与高风险转审批；
- `fullAccess` 多步执行、工具步数上限与结果关联；
- 命令完成、阻塞、继续等待、中断、部分输出继续；
- 目标终端切换和关闭时不会读取错误会话；
- 模型流式文本与工具调用交错时的消息更新；
- 面板重挂载后固定审批栏和历史工具卡仍可见；
- 工具卡状态、按钮、本地化和可访问性；
- 现有 Markdown、表格、配置错误和会话历史回归测试。

工程验证运行 Vitest、TypeScript、ESLint、Prettier、Vite 构建、Rust 测试和 Tauri 调试构建。桌面端真实 shell 阻塞、审批和中断效果由用户最终验收。

## 15. 验收标准

- `ask` 模式批准命令后，AI 等待该命令结果并在同一轮继续回答。
- 拒绝命令后，AI 收到拒绝结果并继续或结束，不丢失当前会话。
- 等待审批、执行、等待输出和阻塞时均显示为活动会话。
- 阻塞时可继续等待、中断或使用当前输出继续。
- `auto` 不自动执行高风险或未知风险命令。
- `fullAccess` 自动执行并回传结果，但有停止和步骤上限。
- 工具卡显示命令、状态、目标、输出摘要和错误。
- AI 面板视觉层级清晰，用户消息、助手正文和工具调用可快速区分。
- 面板关闭重开后，当前内存会话和固定审批栏仍存在。
- 无输出监听器、审批 Promise 或取消控制器泄漏。
- 自动化测试、类型检查、Lint 和构建通过。
